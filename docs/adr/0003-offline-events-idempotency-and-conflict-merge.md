## Context

孩子端在弱网或离线时仍要保留今日任务、StudySession、Attempt 和上传意图。学习过程不可因重试、重连或多设备而被覆盖。现有 Profile/Device 写接口已验证 `Idempotency-Key` 的语义，但尚未定义任务/会话事件协议、服务器版本与冲突处理。

## Decision Drivers

- Attempt 与 AuditEvent 必须追加写、可追溯且不能静默丢失。
- 重试必须有界、可观察，且相同请求不产生重复副作用。
- 需要兼容旧客户端队列，并避免把不可信客户端时间作为排序真相。

## Considered Options

1. 客户端本地状态直接最后写入覆盖服务端状态。
2. 为所有实体使用全局 CRDT。
3. SQLite 追加队列 + 版本化命令/事件 + 服务端幂等记录和按领域定义的合并策略。

## Decision

提议选择选项 3。端侧 SQLite 只保存缓存和待同步队列；每条可写操作携带稳定事件 ID、`Idempotency-Key`、Schema 版本、设备标识和服务端已知版本。API 对同一键和等价载荷返回原业务结果，对同键不同载荷拒绝并审计。Attempt/AuditEvent 只追加；任务的派生状态由服务端版本和显式状态机合并，冲突返回可诊断结果，不采用最后写入覆盖。具体事件字段、保留期限和冲突 UX 在 TODO-007 的契约设计中固化。

## Consequences

### Positive

- 网络重试和应用重启不会自然产生重复 Attempt 或丢失本地操作。
- 服务端可重算派生状态并审计冲突、拒绝和重试。

### Negative / Trade-offs

- 客户端与 API 都需要版本、队列状态和失败恢复逻辑。
- 某些冲突必须显示给用户或家长，而非自动伪造成功。

### Risks and Mitigations

- 风险：队列永久卡住；缓解：区分可重试、需登录恢复、需升级和永久 Schema 错误，提供可观测指标。
- 风险：旧客户端事件不兼容；缓解：版本化 Schema、可读错误码、最短支持窗口与弃用公告。

## Compatibility and Migration

- 兼容性：当前 Profile/Device 的幂等语义保持；任务/会话协议新增而不修改既有路径。
- 迁移步骤：先在 `packages/contracts` 定义版本化事件与结果，再实现 PostgreSQL 幂等存储、客户端队列和断网集成测试。
- 回滚：优先停止新命令发放或向前兼容解析旧事件；不得清空队列、删除 Attempt 或以数据回滚掩盖冲突。

## Validation

- 覆盖重复提交、同键异载荷、断网重连、并发设备、过期版本和局部失败。
- 验证 Attempt/AuditEvent 追加性、服务端版本合并和队列可观测指标。
