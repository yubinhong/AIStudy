# ADR-0019：孩子管理聚合与多孩子工作台作用域

- 状态：`Proposed`
- 日期：`2026-07-18`
- Owner：项目 Owner + API/Web 负责人
- 决策者：项目 Owner（用户已批准一体化产品方向；本 ADR 的分表、事务与迁移细节待实现前确认）
- 关联：`PLAN-0013`、`TODO-015`、`FR-001`、`FR-016`、`ADR-0005`、`ADR-0017`
- 替代/被替代：无；细化 ADR-0005/0017 的 ChildProfile—child Account 关系和 Web 管理体验

## Context

当前 Web 把孩子档案和孩子账号作为两套并列对象：家长先创建/选择 ChildProfile，再单独创建绑定账号。首页还固定读取 `children[0]` 和 `tasks[0]`，只为第一个孩子加载周报。一个家庭有多个孩子时，用户既需要理解内部表关系，也无法确定首页任务、档案和周报属于哪个孩子。

数据库把 `Account` 与 `ChildProfile` 分开有明确安全价值：密码哈希、锁定、启停和会话撤销属于认证生命周期；姓名、年级、教材和科目属于学习档案生命周期。用户要求的是一个自然的“孩子”产品对象，不等于必须把不同安全职责的数据物理合表。

## Decision Drivers

- 创建孩子应是一次可理解、可回滚的操作，不产生孤立档案或孤立账号。
- 密码、会话和账号状态需要与儿童学习资料保持最小权限和不同生命周期。
- 同一孩子不应因重复操作获得多个可登录账号，既有异常数据不能被静默删除。
- 家长切换孩子后，任务、档案和周报必须使用一致且服务端授权的数据作用域。
- 变更必须兼容已有 Profile/Account 数据、幂等写入和自用部署的前滚/回滚。

## Considered Options

1. 维持当前两个表单、两个创建请求和首页首孩子逻辑，仅修改文案。
2. 将 Account 凭据字段直接合并进 ChildProfile 表，并让首页在客户端过滤所有家庭数据。
3. 保持 Account/ChildProfile 分表，在 API 暴露孩子管理聚合、以事务原子创建并增加一对一约束；首页通过已授权 `child_id` 服务端过滤。

## Decision

提议选择选项 3。

1. 家长 Web 只提供一个“创建孩子”表单，提交姓名、年级、教材/科目、用户名和初始密码。一个带 `Idempotency-Key` 的 API 命令在同一 PostgreSQL 事务中创建 ChildProfile 与 child Account；任一校验、用户名冲突或数据库错误使全部写入回滚。
2. `Account` 与 `ChildProfile` 继续分表。聚合读模型可组合展示姓名、年级、用户名和账号状态，但不返回密码、密码哈希、锁定内部值或会话材料。
3. 同一 Household 的一个 ChildProfile 最多绑定一个 child Account。上线约束前先审计既有数据：一对一记录直接保留，无账号档案标为“未开通登录”，多账号绑定阻断自动迁移并由家长人工决定。不得静默合并、改名或删除。
4. 家长账号独立于孩子卡片；每个孩子一张聚合卡集中进入资料编辑、开通/启停登录、密码重置、导出和删除。高风险动作继续遵循 ADR-0017 的重新验证和审计规则。
5. 家长工作台以有效显式 `child_id`、有效最近选择、稳定排序后的首个孩子依次确定当前孩子。问候、今日任务、当前档案和周报使用同一个 ID 并由服务端过滤；家庭孩子总数和未建立孩子归属的设备数保持 Household 级。
6. 查询参数、Cookie 和客户端状态不构成授权。家长只能选择本 Household 的孩子；孩子账号即使篡改 ID 也只能访问绑定档案。无权限资源使用现有统一 403/404 语义，避免枚举。

## Consequences

### Positive

- 产品只暴露一个自然的“孩子”对象，同时保留认证数据的安全隔离。
- 原子写入、幂等和唯一约束减少半创建、重复账号和错误绑定。
- 多孩子数据作用域可见且一致，首页不再隐式依赖数据库返回顺序。

### Negative / Trade-offs

- 需要新增/调整 OpenAPI 聚合 Schema、事务服务、数据审计迁移、Web 状态和浏览器 E2E。
- 资料编辑与账号启停/重置仍是不同安全命令；UI 聚合不能消除其重新验证和错误处理差异。
- 选择持久化会增加少量 URL/Cookie 状态兼容逻辑，服务端渲染必须处理失效孩子。

### Risks and Mitigations

- 风险：既有同档案多账号导致唯一迁移失败；缓解：部署前只读审计、显式报告和人工处置，迁移不得自动删数据。
- 风险：聚合响应泄露认证字段；缓解：使用专用 allowlist Schema，契约/日志测试禁止密码、哈希和会话字段。
- 风险：切换器只改部分组件造成跨孩子混显；缓解：页面级单一 currentChildId，所有 child-scoped loader 强制接收它，并用双孩子 E2E 对账。
- 风险：客户端 ID 篡改造成兄弟姐妹或跨家庭越权；缓解：服务端逐请求验证 Household/角色/绑定，反向授权测试覆盖 URL/Cookie 篡改。

## Compatibility and Migration

- 兼容性：现有读取 Profile/Account 的内部仓储可保留；Web 停止串联两个公开创建请求。公开路径和旧写端点的兼容窗口在 OpenAPI 差异评审中确定，API/Web 必须成对部署。
- 迁移步骤：备份 → 只读基数审计 → 处置重复绑定 → 扩展聚合契约/API → 增加一对一条件唯一约束 → 部署新 Web → 用两个 synthetic 孩子验证 → 收缩旧 Web 写入口。
- 回滚：优先前滚修复。Web 可回退并忽略选择参数，但不得重新允许同档案多账号；数据库不合并/删除两张表。若新约束阻塞旧应用，回退应用和约束前保留审计报告及全部孩子数据。

## Validation

- API：原子成功/校验失败/用户名冲突/数据库故障、同键重放/异载荷冲突、并发创建、一对一约束和跨 Household/兄弟姐妹反向授权。
- 迁移：无账号、一对一、重复绑定三类 synthetic 数据；前滚、重跑、备份恢复和应用回滚。
- Web：一个创建表单、每孩子一张聚合卡、两个孩子切换、刷新恢复、删除当前孩子回退、零孩子空状态、键盘/读屏和错误恢复。
- 数据对账：选择任一孩子后，问候、任务、档案与周报均只引用同一 child UUID；家庭总数和 Household 级设备不随选择变化。
- 安全：CSRF、最近密码重新验证、ID 篡改、日志/HTML/错误响应不含密码、哈希、会话、儿童姓名或其他孩子学习明细。
